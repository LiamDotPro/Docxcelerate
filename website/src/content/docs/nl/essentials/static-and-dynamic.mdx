Elke inhoudsnode is **statisch** of **dynamisch**. Dat onderscheid bepaalt waar
zijn tekst vandaan komt en wat hij kost.

Je verklaart het nooit. De modus volgt uit wat je aanlevert.

## Statische nodes

Geef een alinea zijn tekst en hij lost lokaal op:

```tsx
<Paragraph id="offer">
  Your place starts on {state.startDate}, at {state.college}.
</Paragraph>
```

Hij draait in de preview, in tests en in een build — offline, meteen, gratis. Als
alle nodes van een document statisch zijn, heb je de engine helemaal niet nodig.

## Dynamische nodes

Zet in plaats daarvan **prompts**, plus een placeholder zodat de preview leesbaar
blijft, en de node wordt dynamisch:

```tsx
export const TutorNote: Paragraph = () => {
  const [state] = useState((data: OfferData) => ({
    applicantName: data.applicantName,
    interviewer: data.interviewer,
  }));

  useSetPrompts({
    generalPrompt: `Write two warm sentences about ${state.applicantName}'s interview.`,
  });
  useSetPlaceholders(`A note from ${state.interviewer}.`);

  return <Paragraph id="tutor-note" />;
};
```

Prompts mogen ook props op het element zijn, wat prettiger leest als ze kort
zijn. Props winnen van de hook, dus een aanroeper kan overschrijven wat een
gedeelde hook heeft gezet. `Image` en `Graph` werken hetzelfde — `src` en `data`
zijn daar de leden voor lokale oplossing.

Er zijn vier promptslots beschikbaar. Alleen `generalPrompt` is verplicht:

| Slot | Doel |
| --- | --- |
| `generalPrompt` | Wat de node moet zeggen |
| `infoPrompt` | Context die het model moet hebben maar niet moet herhalen |
| `negativePrompt` | Wat vermeden moet worden |
| `systemPrompt` | Instructies over rol en toon |

## Waarom het wordt afgeleid

Een node die zijn tekst heeft, kan altijd lokaal geproduceerd worden; een node
met alleen prompts nooit. De modus daarnaast verklaren zou een tweede bron van
waarheid zijn die ermee in tegenspraak kan raken, met een of andere
voorrangsregel die beslist wie wint.

In plaats daarvan is de inhoud de waarheid en wordt `mode` daaruit afgeleid. Een
node met eigen tekst is statisch, wat voor prompts een gedeelde hook er ook
omheen heeft gezet — en dat is wat toelaat dat de ene tak geschreven is en de
andere gegenereerd. Beide op **één element** aanleveren is een fout, geen
kruis-of-munt.

`mode` bestaat nog steeds in het gebouwde `DocumentModel` en in `document.json` —
de engine moet weten welke nodes hij moet oplossen. Het is uitvoer, geen invoer.

## Wat je lokaal ziet

Bouwen voor de preview lost dynamische nodes op naar hun **placeholders**, niet
naar gegenereerde tekst:

```ts
const document = await buildProjectPreviewDocument(project);
// dynamic nodes -> placeholder text
```

Dat is opzet. De preview blijft deterministisch en gratis, zodat je aan structuur
en styling kunt werken zonder dat er ook maar één verzoek je machine verlaat. De
placeholder is bovendien een nuttige discipline: is een document met placeholders
onleesbaar, dan doet de structuur te weinig werk.

`usePlaceholderData` geeft je vervangende namen, datums en cijfers, geseed vanuit
waar de component staat — dus dezelfde node toont elke keer dezelfde waarden. Een
preview die zichzelf bij elke build opnieuw schudt, kan niemand nalezen.

## Beslissingen die van de engine zijn

Er is een tweede grens, en het loont die te begrijpen voordat je publiceert.

Wanneer je bouwt met data die je hebt — een preview, een lokale pack, een
document dat ter plekke geschreven wordt — betekent een `if` in een component
precies wat er staat. Hij draait, en er wordt één tak genomen.

Publiceren naar een engine is iets anders. Het artefact wordt **één keer**
gebouwd, tegen vervangende waarden voor een verzoek dat nog niemand heeft gedaan,
en opgeslagen. Een beslissing die van verzoekdata afhangt kan in die build dus
niet vallen; hij moet naar de engine reizen en per document genomen worden.

Daaruit volgen drie regels, en de build handhaaft ze alle drie in plaats van een
verkeerd document bij een ontvanger te laten belanden.

### Per document rekenen, niet per build

Een waarde interpoleren werkt bij het publiceren: hij wordt het token dat de
engine vervangt.

```tsx
<Paragraph id="greeting">Hello {state.name},</Paragraph>
// gepubliceerd als: "Hello {{data.name}},"
```

Ermee rekenen niet, omdat de waarde nog niet bekend is. Een valuta formatteren,
een lijst optellen, een datum vergelijken — dat vraagt om een **deriver**, die de
engine per document uitvoert:

```tsx
<Paragraph
  id="balance"
  derivers={[
    derive("currencyLabel", { output: "balanceLabel", inputs: [dataRef("balanceDue")] }),
  ]}
>
  Your balance is {"{{derived.balanceLabel}}"}.
</Paragraph>
```

`useFormat` en `useDeriver` rekenen tijdens de build, wat juist is zodra de
waarde al bekend is. Grijp naar een deriver wanneer dat niet zo is.

### Lussen worden als lus gepubliceerd

Een vertakking heeft twee takken en beide kunnen gepubliceerd worden. Een lus
heeft er zoveel als het verzoek entries heeft, en dat aantal weet niemand tot er
een document geschreven wordt — dus wat opgeslagen wordt is de lus zelf:

```tsx
<Repeat over="visits" as="visit">
  <Paragraph>Visit: {"{{ctx.visit.label}}"}</Paragraph>
</Repeat>
```

Met echte data loopt hij de collectie meteen af, dus previews tonen de herhaling
in plaats van een beschrijving ervan. Gepubliceerd blijft hij een lus en loopt de
engine hem af, waarbij elke entry onder `as` en de positie onder `indexAs` wordt
gebonden, en kind-ids de index krijgen aangehangen zodat de ene ronde
onderscheidbaar blijft van de volgende.

`.map()` aanroepen op verzoekdata is bij het publiceren een fout die de `Repeat`
noemt die je in plaats daarvan moet schrijven.

### Vertakkingen vermenigvuldigen

Een gepubliceerde vertakking slaat beide takken op, elk onder de conditie die hem
selecteert. Vertakkingen nesten vermenigvuldigt wat een document meedraagt, dus
er is een limiet — `branchLimit`, standaard 32 — en die overschrijden laat de
build falen in plaats van een stilletjes enorm artefact te produceren. Til de
beslissing in een deriver die één waarde oplevert, of verhoog de limiet als het
document echt zo voorwaardelijk is.

## Wat er op het aanvraagmoment gebeurt

Het uploadartefact bewaart waarden voor het aanvraagmoment als tokens zoals
`{{data.residentName}}`, condities als condities en lussen als lussen. Het naar
[de engine](/nl/docs/generation/endpoint/) sturen levert het afgeronde document
op, met dynamische nodes ingevuld en elke beslissing voor deze ontvanger genomen.

De engine is een aparte dienst — hij is bewust geen onderdeel van het npm-pakket,
zodat het installeren van het framework nooit iets meebrengt dat om API-sleutels
of een netwerk vraagt. Richt een workspace op die van jou:

```sh
dxcl init my-documents --api-endpoint https://documents.example.com/api/letters
dxcl init my-documents --no-api-endpoint
```

Je kunt `upload.endpoint` in `docxcelerate.config.json` op elk moment wijzigen.

## Waarom de grens hier ligt

Splitsen op de node in plaats van op het document houdt de gratis helft van de
toolkit echt bruikbaar. Een volledig statisch document is een compleet, werkend
document zonder dienst erachter. Je kiest alleen voor de gehoste helft bij precies
die alinea's die gegenereerde tekst nodig hebben — en je ziet door het template te
lezen exact welke dat zijn.
