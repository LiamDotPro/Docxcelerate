## Writing one

The text is the element's children, interpolated the way JSX children always
are. There's no template language, so formatting, branching and pluralisation are
all ordinary TypeScript — done in the state initializer, which is where a
component does its thinking:

```tsx
import { Paragraph, useState } from "docxcelerate/template";
import type { MemberData } from "../types.ts";

export const Greeting: Paragraph = () => {
  const [state] = useState((data: MemberData) => ({ name: data.memberName }));

  return <Paragraph id="greeting">Dear {state.name},</Paragraph>;
};
```

A component may be `async` — but one that fetches is one that can fail
mid-build, so prefer putting the value in your data first. If you do await,
every hook must be called before the first `await`.

## The token budget

`useAvailableTokens()` is the budget this build allotted, `2000` unless you set
`availableTokens` in the build options. Static nodes can ignore it. Dynamic ones
should spend it:

```tsx
const availableTokens = useAvailableTokens();

useSetPrompts({
  generalPrompt: `Explain the change. At most ${Math.floor(availableTokens / 4)} words.`,
});
```

## Branching

If a document says one of three things, that's one component with three
outcomes — not three components.
Give each arm its own id:

```tsx
if (state.settled) {
  return <Paragraph id="balance-settled">Nothing outstanding.</Paragraph>;
}

return <Paragraph id="balance-arrears">A balance remains.</Paragraph>;
```

Giving each arm its own id is what lets the resolved document record which one
this recipient
got, and they are required once the branch is published — an engine stores both
arms, and an id addresses exactly one node.

When the outcomes differ only in wording, computing the string and returning one
node keeps one id, which is the older habit and still a good one:

```tsx
const [state] = useState((data: MemberData) => ({
  line: data.settled ? "Nothing outstanding." : "A balance remains.",
}));

return <Paragraph id="balance">{state.line}</Paragraph>;
```

## How it sits on the page

`align` is the one appearance a paragraph states for itself, because alignment
is often what the paragraph *is* rather than how it looks — a date is ranged
right in every theme, the way a money column is:

```tsx
<Paragraph id="issued" align="right">{state.issuedOn}</Paragraph>
```

Everything else about how a paragraph is set belongs to the theme, reached by
name through `variant`. The block decides; the node only says which block it is:

```ts
blocks: {
  standfirst: { align: "center", spacingBeforePt: 4, spacingAfterPt: 14 },
  quote:      { indentMm: 10, indentRightMm: 10 },
  heading:    { keepWithNext: true },
  contents:   { tabStopsMm: [{ at: 170, align: "right", leader: "dot" }] },
}
```

```tsx
<Paragraph id="lead" variant="standfirst">What this letter is about.</Paragraph>
<Paragraph id="terms" variant="contents">{"What the agreement covers\t3"}</Paragraph>
```

A node that states its own `align` wins over its block's, the same way a cell
wins over its column. What a block can set, beyond fill, border and type:

| | |
| --- | --- |
| `align` | how the lines sit in the column |
| `spacingBeforePt`, `spacingAfterPt` | space above and below, in points |
| `indentMm`, `indentRightMm` | inset from the left and right margins |
| `firstLineIndentMm` | the first line only — a book's paragraph mark |
| `hangingIndentMm` | the first line pulled back from the rest |
| `keepWithNext`, `keepLines` | never the last thing on a page; never split across one |
| `tabStopsMm` | `[{ at, align?, leader? }]` from the left margin, or from a cell's or shape's inner edge. Put a `\t` in the text to reach one |
| `lineHeight` | leading, as a multiple of the font size |

Each of these means the same thing on screen as it does in Word, and that is
checked rather than assumed: every property here has a conformance case that
packs a document, opens it in Word, and holds the preview to what Word draws to
the millimetre. Two limits fall out of Word's own format and are worth knowing —
padding needs a border to hang on, and a left border pushes the *rule* outward
rather than the text inward.

A paragraph inside a [`<Cell>`](/docs/nodes/table/#what-a-cell-holds) or a
[`<Shape>`](/docs/nodes/shape/) keeps all of this — its own `align` over the
column's, and its variant's indents, tab stops, border and fill — so a
signature cell can carry a dotted leader and a card a ruled quote. There a tab
stop measures from the container's inner edge, and `bleed` and `maxWidthMm`,
which are measures of the page, do nothing.

A border is one solid line unless the block says otherwise. `borderStyle` draws
Word's own `"double"`, `"dashed"` or `"dotted"` rule on every edge the block
draws — a double rule under a grand total, a dashed tear-off line above a
remittance slip — rather than stacking blocks to fake one:

```ts
grandTotal: { border: "1C2340", borderSides: ["bottom"], borderStyle: "double", weight: "bold" },
```

## Lists

A list is paragraphs that say they are items. `list="bullet"` marks one,
`list="number"` counts it:

```tsx
<Paragraph id="intro">To renew:</Paragraph>
<Paragraph id="check" list="number">Check the plan and the price.</Paragraph>
<Paragraph id="pay" list="number">Pay online, or at the desk.</Paragraph>
<Paragraph id="pay-note" list="bullet" listLevel={1}>Card and direct debit are both accepted.</Paragraph>
<Paragraph id="collect" list="number">Collect your new card.</Paragraph>
```

Items written one after another are one list, and the renderer does the
counting — the way it counts pages. That is the whole reason not to type the
numbers: a step dropped for one recipient leaves no gap, and a list built
from your data is a `.map()` like any other.

```tsx
{state.steps.map((step) => <Paragraph id="step" list="number">{step.text}</Paragraph>)}
```

Anything that is not an item ends the list, and a numbered list after it starts
again at one. `listLevel` puts an item under the one above it: `1` for a point
under an item, down to nine deep. Numbers go from figures to letters to roman
numerals as they go down, bullets from a filled dot to an open one to a square.
A bulleted point under a numbered step does not stop the steps counting.

A numbered list counts in figures, then letters, then roman numerals because
that is the default, not because it has to. `listStyle` on the first item at a
level picks that level's numerals for the whole list — a contract's sub-clauses
are `(a)`:

```tsx
<Paragraph list="number">The tenant agrees:</Paragraph>
<Paragraph list="number" listLevel={1} listStyle="lowerLetterParen">to pay the rent on time;</Paragraph>
<Paragraph list="number" listLevel={1}>to keep the property in good order.</Paragraph>
```

`decimal`, `lowerLetter`, `upperLetter`, `lowerRoman` and `upperRoman` are
followed by a full stop; add `Paren` for the bracketed form. Bullets ignore it.

An item is still a paragraph. It has an id, a condition can drop it, it takes a
`variant`, and one an engine writes can be an item like any other. Items stand
together, with the space a paragraph leaves under itself going after the list
rather than between its items — unless the item's own `variant` names a
spacing, which wins.

Two limits. A bullet's glyph and every item's hang are the renderer's, not the
theme's — `listStyle` picks a number's numerals and nothing more. And an item on a `<Shape>` is drawn as a
plain paragraph: the box holds its words off its edge with the same indent a
hang needs.

## Words set differently

`<Text>` sets some of a paragraph's words apart from the rest — the term a
notice turns on, a phrase that leads somewhere:

```tsx
import { Paragraph, Text } from "docxcelerate/template";

<Paragraph id="terms">
  Payment is due within <Text bold>thirty days</Text>. You can{" "}
  <Text href="https://example.com/pay">pay online</Text>.
</Paragraph>
```

`bold`, `italic`, `underline` and `strike` say how the words are stressed;
`script="superscript"` or `"subscript"` raises or drops them — the 2 in m², the
2 in CO₂, the st in 1st — so Word sets them rather than you typing `²`; and
`href` says where they lead: an `https:`, `http:`, `mailto:` or `tel:` address.
One `<Text>` inside another takes both settings. It works the same among the
words of a `<Cell>` or a `<Shape>`.

It is not a node. It has no id and nothing addresses it. It never states a
colour or a size; when a phrase has to stand out — an amount due in a sentence,
a defined term — name a theme block, the way a paragraph does:

```tsx
The amount due is <Text variant="amountDue">{state.due}</Text>.
```

Only the block's character settings reach the words — `color`, `fill` as
shading, `fontSizePt`, `weight`, `font`, `transform`, `letterSpacingEm`;
borders, padding and spacing belong to a paragraph. A mark said beside it wins
over the block, and a link keeps the theme's accent. An address that is none of the four kinds prints as its
words alone, because the address may come out of your data and a preview draws
a link as something a reader can click.

A line end in the text is a line break rather than a new paragraph, which is
what an address wants — one node, three lines, and none of the space a
paragraph leaves under itself:

```tsx
<Paragraph id="address">{"Flat 2\n14 Example Road\nLeeds LS1 4AB"}</Paragraph>
```

Only a static paragraph has runs. One an engine writes is written as plain
words.

### What it publishes

The paragraph keeps its `text` whole, so everything that reads a paragraph's
words still reads one string. The settings travel beside it as `runs`, each
carrying its own words:

```json
{ "kind": "paragraph", "mode": "static", "id": "terms",
  "text": "Payment is due within thirty days.",
  "runs": [
    { "text": "Payment is due within " },
    { "text": "thirty days", "bold": true },
    { "text": "." }
  ] }
```

A paragraph with nothing set apart has no `runs` at all, and publishes exactly
what it did before. Interpolated values work inside a `<Text>` the way they do
anywhere else: a published run holds the token, and the engine settles it in
place, so `<Text bold>{state.name}</Text>` is bold for every recipient
whatever the length of their name.

## Dynamic paragraphs

A dynamic paragraph has no text of its own; it carries prompts and a
placeholder instead, set with `useSetPrompts` and `useSetPlaceholders` or given
as props. Preview builds resolve it to the placeholder and label it; request-time
builds send the prompts. Only `generalPrompt` is required — the fourth variant
below shows what the other three are for.

## Notes

- Both modes resolve to `kind: "paragraph"`. A renderer reads `mode` if it cares
  at all; it never branches on how the node was written.
- A node given its own text is static, whatever prompts a shared hook set around
  it. Supplying both on one element is an error.
- An empty string returns an empty paragraph, not no node. To drop the node,
  return nothing — `false`, `null` and `undefined` are all skipped.
- Renderers escape the text. A paragraph cannot smuggle markup into the page:
  `<Text>` is the only formatting there is, and it is an element, not a string.
