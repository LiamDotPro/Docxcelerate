Every content node is either **static** or **dynamic**. The distinction decides
where its text comes from and what it costs.

You never declare it. The mode follows from what you supply.

## Static nodes

Give a paragraph its text and it resolves locally:

```tsx
<Paragraph id="offer">
  Your place starts on {state.startDate}, at {state.college}.
</Paragraph>
```

It runs in the preview, in tests, and in a build — offline, instantly, free. If
every node in a document is static, you never need the engine at all.

## Dynamic nodes

Set **prompts** instead, plus a placeholder so the preview stays readable, and
the node becomes dynamic:

```tsx
export const TutorNote: Paragraph = () => {
  const [state] = useState((data: OfferData) => ({
    applicantName: data.applicantName,
    interviewer: data.interviewer,
  }));

  useSetPrompts({
    generalPrompt: `Write two warm sentences about ${state.applicantName}'s interview.`,
  });
  useSetPlaceholders(`A note from ${state.interviewer}.`);

  return <Paragraph id="tutor-note" />;
};
```

Prompts can also be props on the element, which reads better when they are
short. Props win over the hook, so a caller can override what a shared hook set.
`Image` and `Graph` work the same way — `src` and `data` are their
local-resolution members.

Four prompt slots are available. Only `generalPrompt` is required:

| Slot | Purpose |
| --- | --- |
| `generalPrompt` | What the node should say |
| `infoPrompt` | Context the model should have but not restate |
| `negativePrompt` | What to avoid |
| `systemPrompt` | Role and tone instructions |

## Why it's inferred

A node that has its text can always be produced locally; a node that has only
prompts never can. Declaring the mode alongside those would be a second source
of truth that could disagree with them, with some precedence rule deciding which
wins.

Instead the content is the truth and `mode` is derived from it. A node given its
own text is static, whatever prompts a shared hook set around it — which is what
lets one arm of a branch be written and the other generated. Supplying both on
**one element** is an error rather than a coin-toss.

`mode` still exists in the built `DocumentModel` and in `document.json` — the
engine needs to know which nodes to resolve. It is output, not input.

## What you see locally

Building for preview resolves dynamic nodes to their **placeholders**, not to
generated prose:

```ts
const document = await buildProjectPreviewDocument(project);
// dynamic nodes -> placeholder text
```

This is deliberate. Preview stays deterministic and free, so you can iterate on
structure and styling without a single request leaving your machine. The
placeholder is also a useful discipline: if a document is unreadable with
placeholders in place, its structure is doing too little work.

`usePlaceholderData` gives you stand-in names, dates and figures, seeded from
where the component sits — so the same node shows the same values every time. A
preview that reshuffles itself on each build is one nobody can proofread.

## Decisions that belong to the engine

There is a second line, and it is worth understanding before you publish.

When you build with data you hold — a preview, a local pack, a document written
on the spot — an `if` in a component means exactly what it says. It runs, and
one arm is taken.

Publishing to an engine is different. The artifact is built **once**, against
stand-in values for a request nobody has made yet, and stored. So a decision
that depends on request data cannot be settled during that build; it has to
travel to the engine and be made per document.

Three rules follow, and the build enforces all three rather than letting a wrong
document reach a recipient.

### Compute per document, not per build

Interpolating a value works while publishing: it becomes the token the engine
substitutes.

```tsx
<Paragraph id="greeting">Hello {state.name},</Paragraph>
// published as: "Hello {{data.name}},"
```

Computing on one does not, because the value is not known yet. Formatting a
currency, totalling a list, comparing a date — those need a **deriver**, which
the engine runs per document:

```tsx
<Paragraph
  id="balance"
  derivers={[
    derive("currencyLabel", { output: "balanceLabel", inputs: [dataRef("balanceDue")] }),
  ]}
>
  Your balance is {"{{derived.balanceLabel}}"}.
</Paragraph>
```

`useFormat` and `useDeriver` compute during the build instead, which is right
whenever the value is already known. Reach for a deriver when it is not.

### Loops are published as loops

A branch has two arms and both can be published. A loop has as many as the
request has entries, and nobody knows that number until a document is written —
so the loop itself is what gets stored:

```tsx
<Repeat over="visits" as="visit">
  <Paragraph>Visit: {"{{ctx.visit.label}}"}</Paragraph>
</Repeat>
```

With real data this walks the collection immediately, so previews show the
repetition rather than a description of it. Published, it stays a loop and the
engine walks it, binding each entry under `as` and its position under `indexAs`,
and suffixing child ids with the index so one pass stays distinguishable from
the next.

Calling `.map()` on request data while publishing is an error that names the
`Repeat` to write instead.

### Branches multiply

Publishing a branch stores both arms, each under the condition that selects it.
Nesting branches multiplies what a document carries, so there is a limit —
`branchLimit`, 32 by default — and passing it fails the build rather than
producing a quietly enormous artifact. Lift the decision into a deriver that
yields one value, or raise the limit if the document really is that conditional.

## What happens at request time

The upload artifact keeps request-time values as tokens like
`{{data.residentName}}`, conditions as conditions, and loops as loops. Sending
it to [the engine](/docs/generation/endpoint/) returns the finished document
with dynamic nodes filled in and every decision made for this recipient.

The engine is a separate service — it is deliberately not part of the npm
package, so installing the framework never pulls in anything that wants API keys
or a network. Point a workspace at yours:

```sh
dxcl init my-documents --api-endpoint https://documents.example.com/api/letters
dxcl init my-documents --no-api-endpoint
```

You can change `upload.endpoint` in `docxcelerate.config.json` at any time.

## Why the line sits here

Splitting on the node rather than the document keeps the free half of the toolkit
genuinely useful. A document that is entirely static is a complete, working
document with no service behind it. You opt into the hosted half only for the
specific paragraphs that need generated prose — and you can see exactly which
ones those are by reading the template.
